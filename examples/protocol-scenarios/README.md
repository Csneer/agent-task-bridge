# 四类产品共用的任务协议场景

这些轨迹用同一份 [`task-core-draft-1`](../../protocol/core-draft/README.md) 实验规格，说明如何围绕人和 Agent 的任务协作构建不同产品。它们验证消息结构与离线行为模型，**不是四个已经运行的业务服务**，也不能发送给当前 v0.1.0 daemon。

每个任务由一个权威服务负责状态。人和 Agent 都可以发起与承接任务；创建时填写目标和预期结果，交付进入 `submitted`，只有发起方对实际交付作出接受决定后才进入 `completed`。预期可以显式修订，旧执行与交付保留原依据；关联任务不自动取得权限或改变彼此状态。

## 场景目录

| 轨迹 | 说明 | 重点检查 |
|---|---|---|
| [接单平台](marketplace.json) | 人类客户发起需求分解，平台选择 Agent，客户在实际交付前后明确预期并要求重做 | 评分 `4.8` 等业务数据可以表达；未被宿主准入的领取被拒绝；执行者不能自验收；修订历史、重做和成功回执重放保留 |
| [企业交付](enterprise.json) | 人类产品负责人发起总任务，Agent 协调需求分析、人工 review、SDD/TDD 规格、全栈确认、实施、测试、运维审批与发布交付 | 人能承接 review/审计/授权任务，Agent 能发起它们；评审意见与发起方最终决定分开；任务拒绝后显式修订重做；各阶段完成不自动完成总任务 |
| [设备任务](devices.json) | 个人通过宿主/网关向设备 Agent 提交采样任务，明确释放旧承接，再由另一设备交付 | 重复上报和交付不会追加成功事件；旧设备迟到交付不能覆盖新承接；设备提交后仍等待个人验收 |
| [个人协作记录](personal.json) | 人和不同 Agent 并行处理个人目标的独立任务，再显式创建汇总任务 | 相同本地任务 ID 在不同 authority 下互不干扰；子任务、同级任务和父任务状态独立；旧依据交付可以由发起者按当前预期接受 |

每份轨迹的 `application_context` 说明产品层已经作出的选择。评分、模型筛选、企业门禁、阶段排序、设备连接和汇总策略都不是核心模型计算的结果。

## 运行检查

在仓库根目录、协议验证依赖已经安装的环境中执行：

```sh
.venv/bin/python tools/check-core-draft.py
```

检查器读取四份 JSON，解析引用、验证实际消息结构并按核心状态规则处理各步骤。每个步骤检查预期状态、任务 revision 和累计成功事件数；针对重复操作、错误角色及旧承接的反例检查明确错误。指定的快照断言还检查父任务或同级任务没有被顺带推进。

依赖准备见[贡献说明](../../CONTRIBUTING.md)。这个 Python 程序只是规格检查工具，不是新的服务实现或 SDK。

## 怎样阅读轨迹

每个文件包含：

- `id`、`description`：场景标识和目标。
- `application_context`：上层产品的预设选择与未实现部分。
- `steps`：有顺序的协议命令、宿主上下文和预期结果。

每个步骤中的 `command` 是协议消息；`context` 是检查器注入的可信宿主上下文，包含参与者及执行/历史读取准入。`context` 不是供客户端自行声明身份和权限的网络认证方案。`expect` 是检查断言，也不是协议请求的一部分。

形如 `${analysis_claimed.task.current_assignment_id}` 的完整字符串是轨迹工具的引用语法，表示读取前一步返回值。检查器会先替换成真实值再验证消息，因此示例不猜测 Assignment、Run 或 Submission ID。这个引用语法只用于测试轨迹，不属于协议字段格式。

任务 `revision` 与预期版本分开：每次成功操作推进 revision；`task.revise` 额外追加预期版本。新 Run 采用开始时的当前版本，随后修订不会覆盖它的依据。Submission 记录执行依据，Decision 记录交付依据和发起方作决定时的评估版本。

成功回执重放可能返回早于任务当前状态的结果。例如设备任务已经 `completed` 后，重试原提交命令仍返回原来的 `submitted` 事实和相同事件 ID；另外的快照断言证明当前任务仍然完成，且没有新增事件。

## 各产品仍需实现什么

**接单平台**仍需注册、模型目录、资格与评分匹配、客户界面、完成率口径、支付和争议处理。示例中的选中 Agent 和拒绝准入是预设宿主输入，评分不会直接成为核心授权。

**企业应用**仍需真实流程编排、SDD/TDD 模板、门禁政策、人工操作界面以及 CI/CD 适配。轨迹先处理需求拒绝和重做，再显式创建后续规格任务；这说明如何用事实驱动门禁，不代表核心已经执行或验证了企业门禁。`summary` 中的代码、测试和发布描述都是预置交付文本，没有实际运行代码、测试或发版。

**设备应用**仍需网关、设备发现、通信、身份映射、离线队列和物理动作对账。示例的协议承接者是设备 Agent；网关中转不自动获得个人的验收身份。任务只有在发起方明确释放后才换承接者，短暂失联不会被模型解释成设备已停止或任务已经失败。

**个人工具**仍需分工、汇报视图、历史接续和汇总逻辑。相同 TaskRef 的状态只由对应权威服务决定，跨服务关系不会创建跨服务事务；汇总是显式的新任务，不是关系字段的隐藏副作用。

这些例子中的 `human` 和 `agent` 都是离线示例身份。人工审批和验收命令是预先编排的输入，不证明真实用户参与、认证或代表关系已经建立。

## 验证边界

这些检查可证明所列消息和反例在同一离线模型中的结果符合草案规则。它们不证明网络可达、数据持久化、崩溃恢复、外部产物有效、独立客户端互操作或生产安全，也不自动证明未列出的所有状态组合正确。

新协议的运行适配、独立实现互操作与真实业务 demo 需要继续按[协议路线图](../../docs/protocol-roadmap.md)验收。[架构说明](../../docs/architecture/protocol-first.md)解释协议核心与这些上层能力的边界。
