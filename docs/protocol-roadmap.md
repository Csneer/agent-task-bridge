## 后续实施顺序

### 1. 验证协议采用成本

用真实接入方检验最小消息和角色能力：发起任务只需表达目标与预期结果；承接、报告、提交和验收不依赖本项目 SDK；人和 Agent 可以分别担任发起者与承接者。记录完成接入所需的代码和宿主职责，避免把认证、网络和业务编排重新塞回任务核心。

采用协议仍需实现或适配消息收发与状态处理。示例、SDK、CLI 和网关可以降低接入成本，但不成为规格的强制依赖。

### 2. 固定一个真实传输与宿主适配

选择并实现一个具体 binding，明确消息映射、可信身份上下文、错误响应、当前任务查询和事件接续。宿主提供身份与准入，服务执行核心版本、承接及交付归属检查。

同时给出持久化、重复请求、重启恢复和历史记录的运行保证。不能把离线模型的进程内状态当作可用的生产存储，也不能把移除核心里的加密格式理解为关闭现有 M1 防护。

### 3. 独立实现互操作

至少两个独立实现通过同一公开规格交换任务操作与结果；参与者中包含人和 Agent，覆盖预期修订、实际交付后验收、重复上报、旧承接迟到和关联任务独立性。读取方通过公开消息或接口恢复相同事实，不读取服务内部数据库。

完成这一阶段后，才可声明新协议具备已验证的运行互操作能力。采用相同 JSON Schema、复用同一模型运行四个 fixture，不满足这个出口。

### 4. 逐个接入业务 demo

| demo | 需要在核心之外补齐的最小服务 | 真实验收重点 |
|---|---|---|
| 接单 | Agent/模型目录、资格匹配、客户入口 | 高评分与模型条件由平台筛选；Agent 交付后由发起方确认；评分更新有独立业务依据 |
| 企业流程 | 阶段编排、人工评审入口、CI/CD 适配 | 拒绝能阻断后续阶段；人的授权/review 作为任务事实保留；发布由明确门禁动作触发 |
| 设备 | 网关、设备连接与离线队列 | 真实任务到达设备；断线重发不重复交付；旧承接不能覆盖新承接；物理动作另有对账 |
| 个人记录 | 多任务视图、分工与汇总 | 多人/Agent 并行任务独立；汇总由显式业务动作生成；重连后历史可接续 |

这些 demo 用来检验同一核心在不同产品中的复用程度，不要求把注册、工作流、设备网络或统计都内置到协议。

## 保留的后续议题

租约与自动回收、通知推送、更多传输映射、跨服务任务权威移交，以及公开市场的信誉、结算和治理，需要独立规格和验收。当前已确认的边界是每个任务保留一个权威服务，并可关联外部任务；没有跨服务原子提交或权威自动迁移。

协议草案、实现支持范围和运行证据分别版本化。新语义不会通过重算摘要覆盖冻结的 M1；后续实现开始前，先明确新旧版本共存、存储与客户端兼容影响。
