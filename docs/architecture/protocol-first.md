# 面向人和 Agent 的任务协议架构

日期：2026-10-31。状态：**本轮架构调整完成，`task-core-draft-1` 实验规格与离线模型已通过验证**。本文描述后续协议方向，不改变已经发布的 `bridge-m1-1` 和 v0.1.0 daemon 行为。当前实现与后续工作分别记录在[协议路线图](../protocol-roadmap.md)。

## 目标：实现共同任务语义，允许不同接入方式

人、Agent 及承载它们的应用，应能按共同规格发起任务、承接工作、报告进展、提交结果，并由发起方决定是否完成。平台可以采用自己的语言、账号、数据库和通信方式；自带 SDK 与 daemon 是可选实现。

协议接入仍需要程序承担消息收发与状态处理。这个程序可以是 Agent 宿主、业务服务、薄客户端或设备网关；模型阅读一份规格不会自动获得通信能力。判断接入是否成立，应看双方能否按相同语义处理同一任务，而不是是否安装了本项目的工具。

每个任务由一个明确的权威服务保存最终状态。不同任务可以属于不同服务，引用使用 `TaskRef = {authority_id, task_id}` 区分。同一任务不会在多个服务间同时拥有不同的权威状态；本轮不实现任务权威迁移或跨服务原子事务。关联外部任务只记录关系。

## 四层职责

| 层 | 统一的内容 | 交给其他层的内容 |
|---|---|---|
| 任务核心 | 参与者引用、任务预期、承接、执行、交付、发起方决定、关联、版本与重复/冲突结果 | 注册评分、模型选择、业务阶段、通信和加密机制 |
| 协作扩展 | 在核心含义不变的前提下，明确增加租约、通知或其他可选行为及采用条件 | 不以任意扩展字段隐式改写完成、承接或验收语义 |
| 宿主与传输适配 | 可信身份上下文、操作准入、消息发送接收、数据持久化与事件交付 | 不自行跳过核心的当前承接者、版本或交付归属检查 |
| 上层产品 | 人机界面、任务匹配、企业流程、审批政策、网关、统计、费用与汇总 | 不直接改写已提交的核心历史事实 |

核心不要求 HTTP、JSON-RPC、MQTT、某种 SDK 或存储产品。具体适配必须声明消息、结果和错误如何传递，提供符合性证据后才能声称支持该协议。当前草案及离线模型并不等于这些适配已经完成。

## 人和 Agent 是参与者，任务角色按场景确定

`ActorRef` 区分 `human` 与 `agent`，两者都可以成为任务的发起者或承接者。类型说明参与者是什么，角色说明它在某个任务中做什么；人类身份本身不附带管理员权限，Agent 身份也不限制其只能执行。

| 任务角色 | 职责 |
|---|---|
| 发起者 | 提供预期结果，记录必要修订，收到实际交付后决定接受或拒绝 |
| 当前承接者 | 明确承接任务，报告执行情况，提交结果或说明无法继续 |
| 评审协作者 | 完成被委派的 review、审批或审计任务，把结果反馈给相应发起者 |
| 读取方 | 在宿主允许的范围内读取任务事实，构建界面、审计或后续业务动作 |

同一个人或 Agent 可以在不同任务中承担不同角色。例如，Agent 发起一项运维审计，人承接并提交意见；Agent 收到审计结果后决定该审计任务是否符合预期。审计结果对发布流程具有什么门禁效力，由企业应用决定。

协作者完成 review 不会自动完成原任务。review 本身可以是关联任务；原任务发起者消费其结果，再明确作出决定。宿主若代表某个人或 Agent 发送消息，必须提供可追溯的真实代表关系，不能仅靠 JSON 中填写一个身份字符串取得其资格。

## 预期结果、实际交付与完成决定分开

创建任务必须给出预期结果 `expected_result`。目标、输入、交付要求和上下文帮助承接者理解工作，但任务不要求发起方预先提供一套不可变的验收算法。

预期可以在协作中进一步明确。通过显式修订操作记录新的预期版本与修改原因，保留旧版本；操作 revision 与预期版本承担不同职责：前者用于避免并发覆盖，后者说明一段工作依据了什么。

执行记录与交付保留其工作依据的预期版本。后续修改不会把已经完成的工作静默标成依据新要求执行，也不会直接判定旧交付合格或不合格。发起者查看实际交付后作出决定，决定记录当时采用的预期版本和理由。因此可以同时看到：最初希望得到什么、后来如何调整、承接者实际交付什么，以及发起者为何接受或拒绝。

共同链路为：

```text
发起任务并填写预期结果
  → 人或 Agent 承接
  → 开始执行与进展报告
  → 正式提交：submitted
  → 发起者查看实际结果并作出决定
      ├─ 接受：completed
      └─ 拒绝：rejected → 发起方明确重开后继续
```

提交只是交付事实，不能自行宣布任务已被发起方验收。设备场景也遵循这一点：设备上报完成后，发起方的应用可以依据自己的政策自动发出接受决定，但协议模型不会省略这个决定或伪造人的 review。

Task、Assignment、Run、Submission 与 Decision 分别保留任务、承接、执行、交付和决定事实。验收拒绝不会改写 Run 曾经执行并提交过的事实。同一任务同时最多一个当前承接者；并行工作使用多个有关联的任务，汇总由上层显式执行。

## 四类场景怎样复用核心

| 场景 | 共同协议链路 | 上层服务负责 |
|---|---|---|
| 接单平台 | 客户或代理发起任务并给出预期结果；被选 Agent 承接、提交；发起方验收，可修订预期并重做 | Agent 注册、等级、完成率、模型目录、评分门槛、匹配排序、支付与争议处理 |
| 企业交付流程 | 各阶段通过关联任务交付规格、代码、测试或评审意见；人和 Agent 分别承接；各任务发起者确认结果 | 阶段依赖、SDD/TDD 规范、发布门禁、审批权限、CI/CD 执行及回退策略 |
| 设备 Agent | 个人或 Agent 发起设备任务；设备或获明确代表资格的网关承接；结果上报成为 Submission；发起者决定完成 | 设备发现、网络连通、MQTT/WebSocket 等传输、离线缓存、设备凭据和物理动作控制 |
| 个人任务记录 | 一个目标关联多个任务；不同 Agent 或人分别承接、汇报和交付；个人或其代理验收；显式创建汇总任务 | 分工策略、个人界面、跨任务进度、汇报汇总和上下文接续 |

### 企业链路的任务粒度

需求分析、拆分与回看 review、规格/SDD/TDD、全栈确认、实施、测试、发布门禁、运维审计、CI/CD 和发版验收，都可以拥有自己的任务与产物。企业应用根据前一任务的交付或决定，显式创建或开放下一阶段。

核心不会把这些业务名称加入通用状态枚举，也不会因一个 review 通过便自动执行发布。需要人确认时，人就是该确认任务的承接者；其意见如何影响下一阶段，是企业应用的门禁规则。拒绝与返工也不会删除此前的规格、交付或评审历史。

### 网关与离线设备的责任

网关可以转发设备消息，也可以在明确的宿主身份映射下代表参与者；网络中转本身不产生任务权限。若网关是实际承接者，设备是其执行端，记录应如实表达这层关系。

核心不根据“暂时连不上”推断设备停止，也不自动推断物理动作失败。旧承接结束并产生新的承接后，旧任务代次不能作为当前交付提交。离线结果如何保存、何时重发、不可逆动作如何对账，需要网关或业务服务实现。自动租约回收属于独立协作扩展，不是所有设备都必须维护的短周期机制。

## 安全与可达性的边界

认证方式、令牌格式、TLS、加密存储、密钥轮换、账号体系与资源可达性由宿主或适配承担。核心不引入统一注册中心，也不指定 grants 数据库或密钥存放方式。

核心仍须明确可信操作发起者、任务权威、当前承接者、目标交付和版本。宿主允许一个操作进入处理后，协议模型仍检查它是否属于当前承接、是否由任务发起者作验收、是否引用正确的交付，以及是否发生并发冲突。身份机制外置不等于任意参与者能修改任意任务。

同键重试返回原提交结果，不制造第二份交付；旧承接的迟到请求不能污染新承接；关联任务不附带权限，也不自动汇总。这些是跨实现共同理解任务所需的行为规则。

## 与已发布 M1 的关系

M1 已验证单权威服务、租约、授权、幂等、交付验收和事件恢复，但把 HTTP/Bearer/TLS、预注册绑定、短租约和较完整的交付契约组合成了一个固定 profile。它继续作为可运行的参考实现保留。

新草案将通用任务语义与这些机制分开，并调整人与 Agent 的参与方式、预期修订及发起方验收模型。这是独立的 `task-core-draft-1`，不是给 M1 关闭鉴权的配置，也不是 M1 客户端可以静默升级的别名。新草案的状态、字段及兼容范围以[草案规格](../../protocol/core-draft/README.md)为准。

本轮交付是架构、机器可读规格、四类场景轨迹及离线行为检查。新协议的真实服务适配、跨实现互操作、持久化恢复与四个完整业务产品仍需分别实施和验收；[路线图](../protocol-roadmap.md)记录其边界。
